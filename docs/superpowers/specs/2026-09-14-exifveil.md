# ExifVeil 1.0 Design Specification

Date: 2026-09-14
Status: Approved for implementation by the reproducible automation workflow
Lane: iOS applications
Seed: `20260914`

## Problem

Photos can carry location, capture-time, device, author, and comment metadata that a person may not intend to share. Existing advice often tells users to inspect settings or trust an opaque cleanup action. ExifVeil should make the evidence visible and create a separate sanitized copy without modifying the original.

## Intended user

An iPhone or iPad user who wants to inspect one local photo before sharing it outside the Photos library.

## Product boundary

- Native SwiftUI application for iOS 17 and later.
- Select one image through `PhotosPicker`; do not request broad photo-library access.
- Process bytes on device. No network calls, telemetry, accounts, background work, or trained model.
- Report sensitive metadata in five understandable categories: location, capture time, device, authorship, and embedded notes.
- Treat metadata absence as "none detected", not proof that an image is anonymous.
- Create a new sanitized image. Never overwrite or delete the selected original.
- Normalize EXIF orientation into pixels before writing so the sanitized image remains upright after the orientation tag is removed.
- Share only through an explicit user action.

## Core flow

1. The user chooses one image with the system picker.
2. The app reads ImageIO properties and maps known keys to explainable findings.
3. A weighted, bounded privacy signal summarizes the inspected metadata. It is not a security guarantee.
4. On request, the app decodes the image, applies the orientation transform, and re-encodes a single-frame JPEG or PNG with no source metadata dictionary.
5. The app re-inspects the output and refuses to present it as ready if sensitive findings remain.
6. The user explicitly shares the new temporary file.

## Architecture

- `MetadataInspector`: ImageIO property extraction plus deterministic key classification.
- `PrivacyReport`: immutable findings, category counts, and bounded risk score.
- `ImageSanitizer`: decode, orient, re-encode, and postcondition audit.
- SwiftUI app: picker, original preview, findings, sanitation status, and `ShareLink`.
- XCTest fixture builder: generates a tiny image containing GPS, timestamp, camera, author, and comment metadata without third-party data.

## Verification plan

- Static repository checks on Windows: project structure, plist/privacy declarations, README style, and generated fixture-schema assertions.
- Swift package tests on hosted macOS.
- XcodeGen project generation and iOS Simulator compilation/tests on hosted macOS.
- Tests cover classification, score bounds, malformed bytes, metadata-bearing fixture inspection, sanitation postcondition, and preserved pixel dimensions after orientation normalization.
- README visual must be a repository-owned diagram of the implemented flow and verified synthetic fixture, not a simulated app screenshot.

## Non-goals

- Batch processing, Photos-library mutation, forensic deletion guarantees, steganography detection, face/object recognition, cloud backup cleanup, video metadata, animated images, or proof that downstream services cannot infer information.

## Main risks

- Re-encoding can change compressed bytes and quality.
- A key outside the explicit classifier may remain unreported; output validation therefore also checks that known sensitive groups are absent.
- Color-profile handling can vary by codec and OS.
- The first release handles one still-image frame only.
